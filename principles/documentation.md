# Documentation

## Purpose

Explain how to write documentation that helps people make decisions and use the system correctly.

## Why it Matters

Documentation captures context that code alone does not communicate. It reduces onboarding time, prevents repeated mistakes, and records important decisions before they are forgotten.

## Core Concepts

- Document purpose, usage, and trade-offs.
- Keep docs close to the thing they describe.
- Link out instead of repeating content.

## When to Use

- Write for the next person who must change the system.
- Keep docs current with the code and workflow they describe.
- Favor short, concrete examples over long explanations.

- Record decisions when the rationale matters later.
- Use stable language and avoid hype.
- Review docs when behavior changes.

## When Not to Use

- Writing docs that restate obvious code.
- Letting docs drift out of date.
- Copying the same explanation into multiple places.

## Benefits

Good documentation takes time to maintain.

## Drawbacks

It prevents far more wasted time in debugging, onboarding, and review.

## Example

A design doc should explain why a module exists, when to use it, and when not to use it.
